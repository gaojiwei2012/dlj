# 2. R001：实际逗留合规、时长与日期规则

- **所属模块**：📊 天数统计
- **类型**：原功能扩展
- **依赖基础**：`stay_records`、`check_in_at`、`check_out_at`、学年、`invalid_date_ranges`、`course_dates`、`Asia/Shanghai`
- **目标**：把现有“按日期是否有逗留”升级为“按实际每日时长和日期规则认定是否符合规定”，首页优先呈现完全符合天数，同时保留部分符合、不符合和各自逗留时长。

## 2.1 基本定义

1. **统计日**：以 `Asia/Shanghai`（UTC+08:00）的一个自然日为单位，而不是以一条签到记录为单位。
2. **4 小时阈值**：当日实际累计在澳门停留时长 **≥ 240 分钟**，才达到时长门槛；不足 240 分钟不达标。
3. **“工作日”在本需求中的含义**：周一至周五，且不属于公共假期/强制无效日。**即使当天没有课程**，达到 4 小时仍可完全符合。
4. **普通周末**：周六、周日默认不能认定为完全符合日；即使达到 4 小时，仍归入部分符合。
5. **有效周末**：老师可以手工把某个周六/周日设为“有效周末”；也可以通过现有课程管理把该日定义为课程日。这两种方式都允许其在满 4 小时时成为完全符合日。
6. **强制排除**：公共假期和老师手工指定的强制无效日优先级最高；即使当天是课程日/有效周末、逗留超过 4 小时，仍为不符合。
7. **没有实际逗留**：标记为 `NO_STAY` / 无记录，不应凭空产生“部分符合”或“不符合”天数。

## 2.2 最终判定矩阵（已确认）

以下表格中的记录均假定该日**实际发生过逗留**：

| 日期条件 | 当日累计时长 | 判定 | 具体原因 |
|---|---:|---|---|
| 公共假期 | 任意 | 🔴 不符合 | 公共假期一律排除 |
| 强制无效日 | 任意 | 🔴 不符合 | 老师强制排除，不允许周末或课程覆盖 |
| 周一～周五，非上述强制排除日期 | ≥ 4h | ✅ 完全符合 | 有无课程均可 |
| 周一～周五，非上述强制排除日期 | ＜ 4h | 🟡 部分符合 | 时长不足 |
| 普通周六/周日，非强制排除 | 任意正时长 | 🟡 部分符合 | 无有效周末/课程日资格 |
| 周末且被标记为有效周末 | ≥ 4h | ✅ 完全符合 | 老师手工授予有效资格 |
| 周末且被标记为课程日 | ≥ 4h | ✅ 完全符合 | 来自现有 `course_dates` |
| 周末有效/课程日 | ＜ 4h | 🟡 部分符合 | 即使日期合格，时长仍不足 |
| 无当日逗留记录 | 0 | 无实际记录 | 不计入上述三类“有逗留天数” |

**一句话公式**：

```text
完全符合 = 有实际逗留
       AND 非公共假期
       AND 非强制无效日
       AND 当日有效停留分钟数 >= 240
       AND [周一至周五 OR (周末 AND (有效周末 OR 课程日))]
```

**优先级（从高到低）**：公共假期/强制无效 → 实际时长门槛 → 工作日或周末有效资格。课程日与有效周末可以覆盖普通周末限制，但不能覆盖公共假期/强制无效日。

### 2.2.1 参考判定伪代码

```js
function evaluateDay({
  hasStay,
  isPublicHoliday,
  isManualInvalid,
  isWeekday,
  isWeekend,
  isValidWeekend,
  isCourseDay,
  stayMinutes
}) {
  if (!hasStay) return 'NO_STAY';
  if (isPublicHoliday || isManualInvalid) return 'NON_COMPLIANT';
  if (stayMinutes < 240) return 'PARTIAL';
  if (isWeekday) return 'COMPLIANT';
  if (isWeekend && (isValidWeekend || isCourseDay)) return 'COMPLIANT';
  return 'PARTIAL';
}
```

## 2.3 时间与跨天计算

### 2.3.1 时间来源

- 服务端生成签到/签退的实际时间，保存为绝对时间（建议 UTC ISO 时间戳）；业务统计统一按 `Asia/Shanghai` 转为北京时间自然日。
- **不需要每次签到时访问外部北京时间 API**。服务器本身须确保系统时钟同步准确，前端传入的本机时间不能作为可信打卡凭证。
- 当天时长采用真实打卡区间在该自然日内的交集计算，不能直接用“签到日期～签退日期的天数”。

### 2.3.2 跨天示例

```text
9月24日 21:00 签到
9月25日 06:30 签退

9月24日：21:00～24:00 = 180 分钟 → 独立评价 9月24日
9月25日：00:00～06:30 = 390 分钟 → 独立评价 9月25日
```

即使连续停留 9.5 小时，也**不能直接把两天都判为完全符合**。两个日期各自查询其星期、公共假期、有效周末、课程日等属性。

### 2.3.3 同日多段和重复记录

同一天若有多段逗留，建议按**时间区间并集**统计分钟数，避免重叠记录重复累计；多条记录覆盖同一自然日仍只生成**一条日级合规结果**。例如 09:00–12:00 与 11:00–15:00，合计实际覆盖 6 小时，不是两段简单相加的 7 小时。

### 2.3.4 OPEN / 进行中的签到

- 正在打卡、当日尚未签退时，可展示**当前累计时长和临时合规提示**。
- R002 的计划差异不能因为今天只打了 2 小时、仍在继续签到，就提前认定当天最终“少完成 1 天”。
- 当日签退后可立即按当前已完成记录重算；若当天之后再次签到，应能继续累加/修正当日结果。

## 2.4 日期规则：复用并扩展现有“无效日期”

### 2.4.1 产品方向（已确认）

**不再额外建一套互不关联的公共假期后台**。把现有“无效日期”升级为统一的 **「日期规则 / 特殊日期」**，其中老师端负责人工维护公共假期、强制无效日与有效周末，系统负责按年份同步周六/周日。原课程管理仍负责上课日。

| 类型（建议枚举） | 产生方式 | 业务含义 | 能否提升为有效 |
|---|---|---|---|
| `PUBLIC_HOLIDAY` | 老师手工录入 | 公共假期：一律不符合 | 不可被课程/有效周末覆盖 |
| `MANUAL_INVALID` | 老师手工录入 | 其他强制无效日期 | 不可被课程/有效周末覆盖 |
| `WEEKEND` | 系统按公历年份自动同步 | 普通周六或周日，默认仅部分符合 | 可由 `VALID_WEEKEND` 或课程日提升 |
| `VALID_WEEKEND` | 老师手工设置 | 此周末允许满 4 小时后完全符合 | 仍受公共假期和强制无效约束 |
| `COURSE_DAY` | 现有课程管理的 `course_dates` | 该日安排课程；若是周末，可提升周末有效资格 | 仍受公共假期和强制无效约束 |

**注意**：`COURSE_DAY` 保留在课程系统中，不强制插入 `invalid_date_ranges`。同一日可能同时是 `WEEKEND`、`COURSE_DAY`、`PUBLIC_HOLIDAY`：这些是不同维度的属性，不应因为“公共假期最高优先级”就删除其他历史属性。

### 2.4.2 老师端需要的日期规则操作

1. 选择公历年份，点击 **「同步本年度周末」**；系统自动生成该年的所有周六/周日。
2. 重复点击“同步”应**幂等**，不能生成重复的周末规则或覆盖老师已经做过的有效周末设置。
3. 老师可新增、编辑、停用公共假期及其他强制无效日期。
4. 老师可以把某个周末设置为**有效周末**，填写原因（例如补课）；也可以撤销该设置。
5. 老师继续通过**现有课程管理**创建/修改/停用课程，其日期自动参与周末有效资格判断。
6. 日期列表应让老师看到：日期、星期、规则类型、来源（自动/手工）、是否课程日、最终业务效果与操作入口。
7. 对已有的日期规则保留基本变更信息，便于解释“为什么这天被算作完全符合或不符合”。

### 2.4.3 推荐的数据改造方式（实现建议，非已实现）

可继续复用 `invalid_date_ranges`，补充 `type`、`source`、状态及必要的原因/操作人信息；也可以在维持旧表兼容的前提下拆出一张日级类型表，正式方案以代码结构为准。

```text
类型建议：PUBLIC_HOLIDAY / MANUAL_INVALID / WEEKEND / VALID_WEEKEND
来源建议：AUTO / MANUAL
旧的“无效日期”历史记录：迁移时应有明确的默认类型与兼容策略
```

**数据库兼容注意**：现有无效日期逻辑可能禁止不同日期段重叠。升级后，周末、公共假期、课程日等属性天然会同日叠加，因此必须调整“禁止任意重叠”的规则，改为按**规则类型和业务冲突**校验；不可继续一概拒绝所有日期重叠。

### 2.4.4 周末同步的年份边界

“同步当年周末”针对**公历年**，而系统学年可能跨两个公历年。日期查询时按实际 `YYYY-MM-DD` 取规则，不能把“2026 年周末同步”误认成已经覆盖整个“2026/2027 学年”。需要时可分别同步 2026 和 2027 年。

## 2.5 统计指标与展示

| 指标 | 定义 | 展示建议 |
|---|---|---|
| `compliantDays` | 完全符合的唯一自然日数量 | 首页**默认最大主指标** |
| `compliantMinutes` | 完全符合日期上对应的实际逗留总分钟 | 辅助显示为小时/分钟 |
| `partialDays` | 有逗留但只部分符合的唯一日期数 | 辅助卡片 |
| `partialMinutes` | 部分符合日期的实际逗留总分钟 | 辅助卡片 |
| `nonCompliantDays` | 公共假期/强制无效日上有实际逗留的唯一日期数 | 辅助卡片 |
| `nonCompliantMinutes` | 不符合日期的实际逗留总分钟 | 可在详情展示 |
| `dailyResults[]` | 每日时长、规则命中项、最终状态和说明 | 日历点开、老师端逐日详情 |

**展示原则**：实际在澳门的日期总量与“完全符合天数”不是同一个数字。没有逗留的日期也不能显示成部分符合日。

## 2.6 手动补录和存量数据

- 正常签到/签退已有精确时间，直接复用。
- 手动补录需增加**入澳日期+时间、离澳日期+时间**；补签退也需要能指定实际离澳时间，否则无法严谨判断每天是否达到 4 小时。
- 对历史只有日期、没有真实时间的记录，**不能未经确认就一律默认满 4 小时**。应明确旧记录迁移/待补正策略，详见第 7 节待确认事项。

## 2.7 R001 验收标准（可据此编写测试）

- [ ] 周三非节假日、无课、逗留 240 分钟：**完全符合**。
- [ ] 周三非节假日、逗留 239 分钟：**部分符合**。
- [ ] 普通周六无课、逗留 600 分钟：**部分符合**。
- [ ] 周六老师设为有效周末、逗留 240 分钟：**完全符合**。
- [ ] 周日安排课程、逗留 240 分钟：**完全符合**，不要求覆盖课程具体时间段。
- [ ] 有效周末/课程周末只逗留 120 分钟：**部分符合**。
- [ ] 公共假期，即使有课、被设为有效周末、逗留 480 分钟：**不符合**。
- [ ] 手工强制无效日与课程日重叠：**不符合**。
- [ ] 跨午夜签到按两个北京时间自然日分别计算。
- [ ] 同一天重叠签到区间不会重复累计分钟数，也不会计两天。
- [ ] 重复同步同一公历年周末不产生重复记录，且不覆盖手工有效周末。
- [ ] 没有实际逗留的日期不计入三类“有逗留”的统计。
- [ ] 首页优先显示 `compliantDays`，同时可查看部分符合、不符合和明细原因。

# 3. R002：计划出行合规预测与实际打卡偏差

- **所属模块**：🎒 出行计划
- **类型**：原功能扩展
- **依赖**：R001 统一日级合规判定器、现有多条 `travel_plans` 和真实打卡记录
- **目标**：让用户知道“计划预计能完成多少个合规日”、“实际完成多少个”，以及**比计划多还是少**；不能让增减互相抵消后掩盖具体偏差。

## 3.1 计划规则（已确认）

1. 一个用户可以创建**多条计划**（原有功能继续保留）。
2. 每条计划以出发日～返回日为覆盖区间，**首尾两日均包含**。
3. 在**计划预测**中，覆盖的每个自然日默认视为停留时长已满足 **≥ 4 小时**；无需用户逐日填写预计时长。这里是预测假设，不代表用户已经实际签到。
4. 计划日期仍必须使用 **R001 同一套日期规则**：工作日、普通周末、有效周末、课程日、公共假期、强制无效日。
5. 多条计划有重叠时，先按用户和自然日合并：同一日只预测、累计一次。
6. 私密计划与公开寻搭子计划都可参与该用户自己的预测；对已删除/失效计划按现有状态定义过滤。

### 3.1.1 计划预测矩阵

| 计划覆盖日期 | 模拟时长 | 预测类别 |
|---|---:|---|
| 周一～周五，非公共假期/非强制无效 | 默认达到 4h | ✅ 计划完全符合 |
| 有效周末或课程周末，非强制无效 | 默认达到 4h | ✅ 计划完全符合 |
| 普通周末 | 默认达到 4h | 🟡 计划部分符合 |
| 公共假期或强制无效日 | 默认达到 4h | 🔴 计划不符合 |

示例：

```text
计划 A：10月10日～10月15日
计划 B：10月14日～10月18日

10月14日、15日不重复计数；先合并为10月10日～18日的唯一日期集合，再逐日预测。
```

## 3.2 计划与实际两套统计

| 分类 | 计算数据 | 用途 |
|---|---|---|
| 全部计划预测 | 所有相关计划日期（含未来）+ R001 日期规则 + 默认满 4h | 告诉学生按现有计划预计可获得多少完全/部分/不符合日 |
| 截至当前应完成 | 已进入可结算范围的计划日 | 用来与实际完成情况公平比较 |
| 实际已完成 | 真实签到/签退，经 R001 计算后的合规日 | 反映真实结果 |
| 日期级执行偏差 | 计划逐日状态 vs 同日实际状态 | 解释为什么与计划不同 |

## 3.3 核心指标：净差异要显示正负方向

```text
netDifferenceDays = actualCompliantDaysToDate - plannedCompliantDaysToDate

> 0：↑ 比计划多 N 天
< 0：↓ 比计划少 N 天
= 0：完全符合天数的净值与计划一致
```

例子：计划截至目前应完成 12 个完全符合日、实际 15 日 → **比计划多 3 天**；实际 9 日 → **比计划少 3 天**。

**注意**：净差异为 0 只说明**数量相同**，并不代表每一天都按原计划执行。

## 3.4 同时保留“偏差明细”（已确认）

| 指标 | 定义 |
|---|---|
| `missedPlannedDays` | 计划该日应**完全符合**，但实际没有达到完全符合的日期数（包括部分符合或无记录）。 |
| `extraCompliantDays` | 计划该日**不要求完全符合**（包括普通周末部分符合预测或没有计划），但实际达到了完全符合的日期数。 |
| `mismatchDays` | 已结算日期内，计划状态与实际状态不同的日期数；它和上面两项的适用范围并非完全相同。 |
| `netDifferenceDays` | 实际完全符合数 − 计划完全符合数；按上述完全符合增减口径，亦等于 `extraCompliantDays - missedPlannedDays`。 |

**示例（净差异掩盖了偏差）**：

| 日期 | 计划 | 实际 | 完全符合数量变化 |
|---|---|---|---|
| 10月5日 | ✅ 完全符合 | 🟡 部分符合 | -1（未兑现） |
| 10月8日 | 无计划 | ✅ 完全符合 | +1（额外完成） |
| 合计 | | | **净差异 0，但存在 2 个偏差日期** |

建议在详情中提供日期、计划类别、实际类别、实际停留时长及差异原因。

### 3.4.1 “计划不符合日”与“实际未出行”的区别

公共假期即使被计划覆盖也预测为“不符合”，但如果当天最后没有签到，**“计划不符合”不能冒充“实际不符合”**。系统应保留 `NO_STAY` 状态，必要时显示为“计划出行但未发生”，便于老师和学生看懂执行差异。

## 3.5 对比时间边界（已确认）

- **未来日期**：参加完整计划预测，但不能因为尚未打卡就算“少完成”。
- **今天存在 OPEN 签到**：显示“进行中”；不可在时长还会增长时提前把当天最终认定为计划未兑现。
- **已经结束的历史日期**：参加正式计划/实际逐日对比。
- **今天已经签退**：可用目前已完成的真实时长立即更新结果；若当天再签到，仍需重新计算。
- 计划与实际汇总应使用**同一个学年、同一截点、同一套 R001 规则版本**，避免不同统计口径产生伪差异。

# 4. R003：自驾寻搭子座位预约与取消预约

- **所属模块**：🎒 寻搭子
- **类型**：在现有公开寻搭子和空余座位展示上新增交互闭环
- **目标**：只有“自驾且有空余座位”的公开计划允许其他登录用户预约 1 个座位；预约成功无需发布者审批，立即扣减座位并展示发布者联系方式；预约人可自行取消并释放座位。

## 4.1 保留原有发布逻辑

用户可以从自己的出行计划点击“寻找搭子/公开寻搭子”，按 V1 现有流程发布城市、出发日、返回日及交通方式。选择自驾时，可声明是否有空余座位及数量（现有允许 1～6）。其他用户仍通过现有公共寻搭子列表发现计划；非自驾或没有可预约座位的计划不出现预约按钮。

## 4.2 预约流程（已确认）

```text
发布者公开寻搭子计划
  → 交通方式为自驾且存在剩余座位
  → 其他用户点击“预约座位”
  → 弹出“是否确认预约？”
  → 用户点击确认
  → 服务端校验权限、座位余量及是否重复预约
  → 立即创建有效预约（RESERVED），无需发布者审批
  → 剩余座位 -1
  → 向这位成功预约的用户返回并展示发布者联系方式
```

**联系方式建议**：在该条公开自驾计划中填写联系方式（类型如微信/手机号/其他，具体 UI 可开发时确认），不强制修改全部用户的基础资料。普通 `/api/companions` 列表不得直接公开私密的联系方式字段。

## 4.3 取消预约流程（已确认）

```text
已预约用户看到“✅ 已预约 / 取消预约”
  → 点击“取消预约”
  → 二次确认
  → 预约状态 RESERVED → CANCELLED
  → 剩余座位 +1
  → 该座位重新对其他用户开放
  → 当前页面不再展示该条计划的发布者联系方式
```

**隐私现实边界**：取消预约以后，系统可以撤回界面/接口上的联系方式查看权限，但**无法保证用户没有提前截图或记下已展示的信息**。

## 4.4 必须遵守的业务约束

| 条件 | 规则 |
|---|---|
| 登录鉴权 | 预约和取消预约均需现有 Session 鉴权。 |
| 计划归属 | 发布者本人不能预约自己的座位。 |
| 每人每计划 | 同一用户对同一计划最多只能有 **1 个有效预约**。 |
| 计划类型 | 仅公开、有效且自驾、有座位的计划可预约。 |
| 空余座位 | 大于 0 才允许新预约；为 0 时显示“已满”，不允许出现负数。 |
| 取消权限 | 仅该预约用户本人能取消自己的有效预约。 |
| 重复取消 | 已取消的记录不能被再次取消并重复返还座位。 |
| 并发 | “最后一个座位”同时被多人预约时只能成功一个；扣减和预约写入必须处于同一事务。 |
| 联系方式 | 只向发布者本人及当前有效预约用户展示；取消后停止继续下发。 |
| 已满展示 | 可继续保留公开计划卡片，标记“已满”，无需强制隐藏整条计划。 |

## 4.5 推荐数据模型（建议，尚未落地）

```text
travel_plans：沿用现有计划表
  + contact_type         // 联系方式类型
  + contact_value        // 联系方式值，非公开列表字段
  + 座位总量/剩余量一致性机制

travel_seat_reservations（新增）
  id
  travel_plan_id
  user_id
  status               // RESERVED / CANCELLED
  created_at
  cancelled_at
```

**座位统计一致性**：可沿用原 `seat_count` 表示剩余座位，但要避免“被预约后修改原座位数”导致逻辑混乱。推荐同时保存初始可约总量，或从“初始座位量－有效预约人数”推导剩余量。无论采用哪种实现，预约/取消均须保证数据库层面的一致性。

## 4.6 接口建议（路径仅供开发设计，并非 V1 已有接口）

| 方法 | 建议路径 | 行为 |
|---|---|---|
| POST | `/api/travel-plans/:id/reservations` | 当前用户确认预约；成功返回预约状态、剩余座位、授权联系方式。 |
| DELETE 或 POST | `/api/travel-plans/:id/reservations/me` | 当前用户取消自己的预约；成功释放 1 座位。 |
| GET | `/api/companions`（扩展既有接口） | 列表新增剩余座位、`isReservedByMe`、是否已满等必要展示字段，**不向未授权者下发联系方式**。 |

## 4.7 R003 验收标准

- [ ] 发布自驾计划，有 3 个空余座位；A 预约成功后剩 2，并能看到联系方式。
- [ ] A 再点同一计划，显示“已预约 / 取消预约”，不会重复占位。
- [ ] 发布者本人无法预约自己。
- [ ] A 取消后剩余座位恢复 3，状态标记 `CANCELLED`，当前页面不再显示联系方式。
- [ ] A 重复提交取消请求时，不会再次增加座位。
- [ ] 仅 A 可以取消 A 的预约，B 不可代为取消。
- [ ] 剩余座位为 0 时不可继续预约；两个用户并发抢最后一座时仅一个成功。
- [ ] 未预约的普通列表访问者无法从 API 响应中直接获得发布者联系方式。

## 5.5 数据与接口复用要求

```text
签到/签退记录 ──→ R001 合规计算 ────────┐
                                         ├──→ R004 老师端学生总览/详情
出行计划 ────────→ R002 计划预测与偏差 ───┘
                        ↑
                   复用 R001 日期规则

R004 老师端日期规则管理 UI ──→ R001 规则配置/数据表
```

- R004 的新 API 继续走服务端 ADMIN 权限校验。
- 规则配置变化后，相应学年、学生实际合规与计划预测需要重新计算/使缓存失效，以避免老师修改有效周末后两端数字不一致。
- 如扩展 CSV，应保留原导出能力，并可新增完全/部分/不符合与计划差异等列；不能让旧导出字段突然变义而未做兼容处理。
- 关键规则修改建议继续写入既有 `audit_logs`，包含操作者、变更前后与原因。

## 5.6 R004 验收标准

- [ ] ADMIN 可查看全部学生并打开其中任意一个学生详情；普通 USER 不可访问管理员学生接口。
- [ ] 老师看到的 R001 合规结果与该学生自己看到的完全一致。
- [ ] 老师看到的 R002 净差异、偏差明细与学生端一致。
- [ ] 老师能同步本年度周末，重复同步不重复创建且不覆盖人工配置。
- [ ] 老师能设置/撤销有效周末，修改后受影响日期的 R001/R002 结果正确更新。
- [ ] 老师能录入公共假期和强制无效日，它们优先于有效周末/课程日。
- [ ] 现有课程管理仍可定义课程日，日期规则页面能看见其影响。
- [ ] R004 不引入未经确认的 teacher_id/班级数据隔离规则。

# 6. 跨需求技术实现清单（供后续拆开发任务）

以下是**实现建议**，不是已发布接口或已创建字段。

## 6.1 共享计算层

建议抽出统一的 `Daily Compliance Engine`，输入某一用户某一北京时间自然日的分钟数和日期属性，输出：

```json
{
  "date": "YYYY-MM-DD",
  "stayMinutes": 300,
  "isPublicHoliday": false,
  "isManualInvalid": false,
  "isWeekend": true,
  "isValidWeekend": true,
  "isCourseDay": false,
  "status": "COMPLIANT",
  "reasonCode": "VALID_WEEKEND_OVER_4H"
}
```

R001 传入真实时间区间折算出的 `stayMinutes`；R002 则对计划覆盖的每一日按默认达到 240 分钟调用**同一个规则引擎**；R004 不重复计算，只读取 R001/R002 的业务结果。

# 7. 待确认项与既有问题（不擅自扩大为已确认需求）

这些问题不推翻上面的**已确认核心规则**，但正式编码前应明确其处理方式。

| 编号 | 问题 | 当前文档的处理 |
|---|---|---|
| Q01 | V1 历史“手动补录”若只有日期没有时刻，如何判定 4 小时？ | **待确认**：建议标记“时长未知/待补正”，不擅自默认符合。 |
| Q02 | 已创建的出行计划后来被修改日期，历史计划偏差是否按“当前最新计划”回算，还是保留当时计划快照？ | **待确认**；第一版可采用当前有效计划口径，但需要界面说明。 |
| Q03 | 预约成功后，发布者删除计划/取消公开/修改座位数，现有有效预约如何处理？ | **待确认交互策略**；技术上必须确保剩余量不能低于已预约人数，并避免静默丢失有效预约。 |
| Q04 | 用户取消预约后，若还有空位是否允许再次预约？ | 建议允许再次预约，但每时刻仅一个 `RESERVED`；仍可按产品要求限制。 |
| Q05 | 公共假期手工录入是单日、日期段，还是同时支持批量文件导入？ | **已确认第一阶段为老师手工维护（方案 A）**；CSV/自动接入外部官方假期是后续可选扩展，不应冒充已确认。 |
| Q06 | 原有 `invalid_date_ranges` 的历史数据默认映射为哪一类？ | 迁移策略待代码落地时确认，建议默认归入 `MANUAL_INVALID` 并保留原有生效效果。 |
| B01 | 学年之外的历史逗留日期，日历 `isPresent` 是否应该仍显示？ | V1 代码与已有测试口径存在差异，需单独裁定。 |

# 8. 整体完成定义（Definition of Done）

当本轮 R001–R004 正式完成时，应同时满足：

1. **业务一致**：学生端、老师端、计划预测调用同一套日期合规规则；规则变更后各处统计一致。
2. **日期正确**：以北京时间自然日独立拆分，4 小时阈值边界、跨日、多段重复、课程日/有效周末/公共假期优先级符合验收表。
3. **统计可解释**：不仅给出完全/部分/不符合总数，还能看到每日时长和原因；计划差异既有多/少净值，也有日期级偏差明细。
4. **预约闭环**：自驾预约、取消、扣减/返还座位、隐私和重复/并发保护均通过测试。
5. **老师可管理**：在现有 ADMIN 权限下查看全部学生合规与计划情况，维护日期规则及年度周末同步；不重复登记或计算 R001/R002。
6. **向后兼容**：保留既有登录鉴权、签到/签退、课程、公开寻搭子、学年、导出和部署能力；历史数据采用经确认的迁移办法。
7. **状态真实**：需求表将“V1 已有基础”“新增完成”“仍待确认”分别标记，不以页面原型替代实际后端验收。
